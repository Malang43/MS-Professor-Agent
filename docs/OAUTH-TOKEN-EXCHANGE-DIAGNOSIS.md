# Gmail token-exchange investigation (2026-10-21)

The owner supplied the production category oauth_callback_failure token_exchange after ff3e81d. This proves execution passed state lookup/expiry, per-attempt cookie binding, active initiating session, atomic state consumption and PKCE decryption. Token encryption and connection persistence had not yet begun. It does not prove Google returned an HTTP rejection: transport and token-response parsing failures share this stage.

Verified request: HTTPS POST https://oauth2.googleapis.com/token, application/x-www-form-urlencoded, client_id/client_secret, grant_type=authorization_code, code, code_verifier and redirect_uri. Both authorization and redemption construct redirect_uri from APP_ORIGIN plus /api/oauth/gmail/callback; forwarded hosts do not determine it. Expected production URI is https://ms-professor-agent-malang43.vercel.app/api/oauth/gmail/callback, matching the owner's confirmed Google registration. Existing proxy regression covers a rewritten Worker URL and hostile forwarded-host headers.

Cloudflare secret bindings establish presence, not ID/secret pairing. No credential values were retrieved or changed in this investigation. Matching the replacement ID and secret to the same enabled Google Web client cannot be independently certified from opaque secret metadata. No real token request or OAuth attempt was made. Historical telemetry access was previously denied (403); no historical Google status/error category is available. A mismatched secret is therefore a hypothesis, not a verified root cause.

Verified diagnostic defect: providerRequest discards non-success HTTP status/error bodies, so the generic public error hides the distinction. The local fix adds an authorization-code-only wrapper. It logs oauth_token_exchange_failure, numeric status (0 for transport failure), and only a fixed allowlist of OAuth error names or fixed parsing/transport categories. Error bodies are bounded at 8 KiB; descriptions, tokens and arbitrary values are discarded. Successful tokens are never logged. Public errors and provider retry classifications remain unchanged; redemption is never retried automatically. Mailbox reads, sends and refreshes do not use this wrapper.

An observed invalid_client would implicate client authentication/configuration and require checking the same Google Web client entry; it does not alone prove which credential is wrong. invalid_grant would require checking code validity, timing, client/redirect binding and PKCE. Transport or unreadable-body categories require their own investigation. No credential or security change is justified before that evidence.

## Verified Workers runtime defect (follow-up)

The owner reported oauth_token_exchange_failure 0 transport_failure. The unchanged implementation was exercised in local workerd/Miniflare with compatibility date 2026-10-01, synthetic credentials and an outbound-service stub intercepting all requests. It emitted the same failure and made zero outbound calls. A direct synthetic runtime probe identified TypeError: Invalid redirect value; Workers accepts follow or manual, not error. AbortSignal.timeout was available. Direct, detached and explicitly bound fetch calls all failed with the same redirect option; loss of this binding was not the cause.

providerRequest placed timeout creation, option construction and the fetch invocation inside one catch, replacing every exception with ProviderError. oauthTokenRequest then inferred transport_failure solely because no response status had been assigned. Consequently a local Request construction/runtime exception was mislabeled as a network failure. This reproducible defect prevents the deployed path from reaching Google. No evidence from this failure establishes a credential mismatch, DNS problem or Google rejection. A subsequent Google response after fixing this defect remains unverified.

The minimal local fix changes providerRequest to redirect=manual. Existing non-success handling rejects 301/302/303/307/308; there is no automatic redirect or credential forwarding to Location. The same helper is shared with other provider calls, which retain their existing error/retry classifications and no automatic code-redemption retry. No timeout or security limit is relaxed. Other direct adapters outside this helper are not changed.

The authorization-code diagnostic wrapper now validates Request options locally and tracks fixed categories: request_setup_exception (before the observed fetch), request_validation_exception, fetch_timeout, fetch_aborted, fetch_type_error, fetch_exception and response_processing_exception. A fetch TypeError is intentionally not asserted to be a network outage: fetch can also reject locally. Provider messages, stacks, causes, codes, body data and tokens are never logged. HTTP statuses and allowlisted Google error categories remain available. No new OAuth attempt was made.

Validation: 112 unit tests passed; both workspace TypeScript checks and production build passed. Run node scripts/check-oauth-runtime.cjs for offline Workers runtime checks: original redirect mode fails before network; fixed synthetic exchange succeeds; each of five redirect statuses is rejected after exactly one intercepted request. All outbound Worker requests in that test are stubbed; no real Google request or credentials are used.

Source: https://developers.cloudflare.com/workers/runtime-apis/request/ (Workers Request redirect modes). The decisive evidence is the actual runtime reproduction, not an inferred network or credential failure.
