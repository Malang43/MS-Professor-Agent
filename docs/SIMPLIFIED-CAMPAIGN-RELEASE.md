# Simplified campaign production release — October 27, 2026

The existing Next.js/Vercel frontend and Cloudflare Worker/D1/KV integrations are preserved. Upload Excel or CSV in Professors, choose Manual / Use Excel content or AI-assisted preparation, then choose individual review or complete campaign review. Campaigns support 25 rows within the existing Free-plan request budget; professor-only imports retain 500-row support.

Manual preparation preserves supplied subjects, bodies (including whitespace), UTC scheduled timestamps, IANA timezones and exact follow-up proposals. AI uses the existing verified-source/Groq safeguards and visibly reports template fallback. Invalid rows and duplicate/existing schedules are reported. Uploading and preparation never authorize delivery.

Complete review shows the Gmail account, included/excluded recipients, expandable initial content, exact conditional follow-ups, delays, times and maximum authorized message count. The primary approval action explicitly authorizes both categories. Existing D1 batch approval atomically persists all included initial schedules, exact follow-up rules, immutable consent snapshots and the campaign name. Mixed initial-only and follow-up rows are supported. Success appears only after persistence; no Outreach revisit or second approval is required. Individual review supports editing initial subjects/bodies, exclusions and per-recipient combined approval. Future initial messages and follow-ups can be cancelled; cancellation is safely retryable.

Migration 0008 is additive: it adds deleted_email to professor tombstones, a campaign name, and explicit suppression precedence. A later explicit import preserves the old record as deleted, retains its original address in deleted_email, replaces only its unique-key address with an ID-based deleted.invalid tombstone, and creates a fresh active record. Old messages, transports, provider receipts, approvals and cancelled automation remain attached to the deleted record. Only deletion-only suppression may be released, and historical decline/opt-out/bounce evidence prevents even that release. Explicit manual blocks and opt-outs remain enforced. Import release/new-record creation is one transaction. No existing data is rewritten merely by deployment.

Transactional authentication email is disabled by production configuration (MAIL_PROVIDER=disabled, MAIL_DELIVERY_ENABLED=false); provider code, secrets and verification/token schema remain for future integration. The unavailable verification control explains the restriction. Password sign-in, passkey sign-in, forgot-password access and saved-code recovery are visible. Signup continues using the original Turnstile widget and server-side Siteverify. Recovery code hashing, single use, session revocation, passkey verification and rate limiting are unchanged. Unverified users retain private dashboard/profile/professor/document access while mailbox actions retain the existing verification/legacy-account policy. No address is falsely marked verified.

Validation: 267 automated tests passed; both workspace TypeScript checks and the production build passed; production and full dependency audits found zero vulnerabilities. Native Workers runtime checks passed for signed WebAuthn, intercepted Turnstile Siteverify, Gmail send/thread/reply/profile HTTP and OAuth redirects. Browser verification used an isolated database, synthetic Gmail credentials and no real delivery: actual XLSX → Manual → complete review → single approval → persisted success, cancellation, individual edits/approval, AI safe fallback, and mobile layout. No real campaign was approved or sent in production.

Browser regression source: scripts/campaign-browser.cjs. Run from repository root after building, with Playwright available; optional PLAYWRIGHT_MODULE_PATH and PLAYWRIGHT_CHROMIUM_EXECUTABLE select an existing local installation. Production checks compare hash-only baselines for accounts, encrypted connections, documents, receipts, messages, approvals, authorized follow-ups, professors, suppressions, recovery codes and passkeys, plus unrelated Worker bindings.

Remaining policy limitation: unverified accounts cannot connect Gmail or approve/send campaigns while verification delivery is unavailable. This release preserves that explicitly requested policy; passkeys and recovery codes recover account access without granting email verification. No provider was purchased or new infrastructure created.
